# 项目级 AI 工作台功能需求文档

## 1. 背景

当前产品已经具备桌面端、Web 端、Android 端、后端服务和会话管理能力，但在实际项目协作场景中仍存在几个明显问题：

- Android 新版本中，旧版本已支持的多主机扫描、添加、切换和管理能力缺失或不可用。
- Android 对话体验还不够完整，会话切换存在卡顿，运行中、已完成、失败等状态不够清晰。
- 项目层目前更像多个对话的管理集合，缺少面向真实软件交付的需求、方案、执行、验收和归档工作流。
- Desktop App 是执行器环境，需要提供清晰的连接信息和可发现能力，供 Android 扫描并保存多个 Desktop。

本需求文档用于明确下一阶段功能范围，避免把恢复旧能力误扩展为过度复杂的新架构，同时推动产品从“多对话管理器”升级为“项目级 AI 工作台”。

## 2. 产品目标

### 2.1 短期目标

- 恢复 Android 端旧版本已有的多主机扫描与管理能力。
- 优化 Android 端对话切换性能与任务状态展示。
- 在 Desktop App 中补齐执行器连接信息、局域网可访问提示和移动端连接引导。
- 统一多端对主机连接、会话状态、任务状态的基础表达。

### 2.2 中期目标

- 强化项目层能力，使项目不只是会话集合，而是完整工作空间。
- 支持需求、方案、任务、验收、文档归档等项目管理对象。
- 支持多个 worker 并行执行任务，同时避免互相污染 Git 工作区。

### 2.3 长期目标

- 将人类软件项目管理中的最佳实践产品化。
- 让 AI agent 的执行过程可计划、可追踪、可验收、可归档。
- 形成适合真实商业项目交付的项目级 AI 工作台。

## 3. 范围说明

### 3.1 本阶段包含

- Android 多主机扫描与管理恢复。
- Android 对话状态与完成反馈优化。
- Desktop 执行器连接信息与可发现性。
- 项目级需求、方案、执行、验收、归档能力设计。
- 多 worker 并行执行与 Git 隔离工作流设计。

### 3.2 本阶段不包含

- 不把 Android 多主机能力重新设计成复杂 runtime 类型系统。
- 不引入本地 runtime、容器 runtime、SSH runtime、云 runtime 等新分类体系。
- 不强制改变旧版本已经可用的主机连接协议，除非确认旧协议无法继续使用。
- 不在切换到未完成对话时弹出“任务仍在运行”提示。
- 不在长时间无输出时提示“可能卡住”。

## 4. 用户角色

### 4.1 普通开发者

- 在桌面端或 Android 端连接一台或多台主机。
- 创建项目、查看会话、接管任务、查看执行状态。
- 关注任务是否完成、失败或需要处理。

### 4.2 项目负责人

- 管理需求、方案、任务和验收结果。
- 将 AI 执行过程沉淀为项目文档。
- 查看项目整体进展和风险。

### 4.3 高级用户

- 使用多个 worker 并行推进多个任务。
- 查看每个 worker 的工作区、分支、diff、测试结果和合并状态。
- 处理 Git 冲突、回滚或放弃某个 worker 的改动。

## 5. Android 多主机管理恢复

### 5.1 背景

Android 端旧版本曾支持多台主机的扫描、添加、切换和管理。新版本中该能力缺失或不可用，导致用户无法方便地连接不同主机，也无法维护已保存主机。

本需求重点是恢复旧能力，不重新发明一套 runtime 管理系统。

### 5.2 功能需求

- 支持通过公开健康检查接口被 Android 局域网扫描发现。
- 支持提示防火墙、监听地址和移动端连接前置条件。
- 支持保存多个主机配置。
- 支持在已保存主机之间切换。
- 支持编辑已保存主机配置。
- 支持删除已保存主机配置。
- 支持显示当前连接主机。
- 支持连接测试或基础连接状态展示。
- 如旧版本支持默认主机或最近使用主机，应恢复该行为。
- 如旧版本支持扫描结果去重，应恢复该行为。
- 如旧版本支持扫描失败原因展示，应恢复该行为。

### 5.3 页面与交互

Android 端应提供清晰的主机入口，推荐包含以下区域：

- 当前主机：显示正在连接或最近连接的主机。
- 已保存主机：展示用户保存过的主机列表。
- 扫描发现：展示当前网络中扫描到的可连接主机。
- 手动添加：允许用户输入主机地址、端口、名称等必要信息。
- 主机详情：支持查看、测试连接、编辑和删除。

### 5.4 状态要求

主机连接至少需要表达以下状态：

- 未连接。
- 连接中。
- 已连接。
- 连接失败。
- 不可达。

状态展示应以列表内标识和详情页状态为主，不应频繁打断用户。

### 5.5 非目标

- 不新增复杂 runtime 类型抽象。
- 不区分本地、远程、容器、SSH、云端等 runtime 类型。
- 不要求运行中的任务动态切换主机。
- 不改变旧版本主机管理的数据结构，除非迁移是恢复能力所必需。

## 6. Android 对话体验优化

### 6.1 背景

Android 端目前在多对话场景下体验不足，主要表现为切换卡顿、运行状态不可见、完成状态不可见、完成反馈不足。

### 6.2 功能需求

- 优化对话切换性能。
- 对话列表显示运行中状态。
- 对话列表显示已完成状态。
- 对话列表显示失败状态。
- 当前对话页显示任务执行状态。
- 当前对话页显示任务完成状态。
- 当前对话页显示任务失败状态。
- 任务完成后提供明确完成反馈。
- 后台运行的对话应能在列表中被识别。
- 新完成任务可在会话列表中展示未读或新完成标识，用户进入会话后取消该标识。

### 6.3 推荐状态模型

会话任务状态建议沿用当前产品文档中的基础状态：

- `idle`：空闲。
- `running`：运行中。
- `waiting_for_input`：等待用户输入。
- `completed`：已完成。
- `failed`：失败。
- `needs_attention`：需要用户关注。

状态模型应由后端、Web、Desktop、Android 共享，避免多端各自定义相近但不一致的状态。

### 6.4 性能要求

- 切换对话时优先展示本地缓存内容。
- 长对话应避免一次性渲染全部消息。
- 会话列表应避免因单个会话状态更新导致全列表重渲染。
- WebSocket 高频事件应合并或节流后再更新 UI。
- 加载态、空状态、错误态应明确，避免用户误以为应用卡死。

### 6.5 非目标

- 切换到未完成对话时，不弹出“该任务仍在运行”提示。
- 长时间无输出时，不提示“仍在运行 / 可能卡住 / 查看日志”。
- 不把 Android 端做成桌面端完整复杂面板，优先覆盖查看、提醒、接管和轻量审批。

## 7. Desktop 执行器连接信息与可发现性

### 7.1 背景

Desktop App 在本产品关系中是执行器环境，不是扫描和管理其他主机的客户端。Android 端需要扫描、添加并切换多个 Desktop；Desktop 端需要保证自己可被发现、可被连接，并向用户展示必要连接信息。

### 7.2 功能需求

- 支持通过公开健康检查接口被 Android 局域网扫描发现。
- 支持展示本机可连接地址、端口和服务状态。
- 支持展示 Android 端连接引导。
- 支持提示防火墙、监听地址和移动端连接前置条件。
- 支持展示当前执行器服务是否可被局域网访问。
- 支持展示服务版本和基础健康状态。
- 不在 Desktop 中管理或切换其他 Desktop 主机。
- Android 端负责连接测试。
- Desktop 端负责显示自身执行器状态。

### 7.3 推荐入口

Desktop App 推荐在以下位置提供入口：

- 设置页中的“主机管理”。
- 顶部或侧边栏当前主机选择器。
- 首次启动或未连接状态下的引导入口。

### 7.4 与 Android 的一致性

Desktop 与 Android 应共享主机字段、连接状态、错误码和基础行为，减少多端理解成本。

## 8. 项目级工作流

### 8.1 背景

当前项目层较薄，更像多个对话的集合。真实软件项目中，用户需要的不只是聊天记录，而是围绕需求推进的一整套工作流。

项目层应升级为可持续推进的软件交付空间。

### 8.2 项目对象

项目应包含以下核心对象：

- 项目概览。
- 需求。
- 方案。
- 任务。
- Worker。
- 验收记录。
- 文档归档。
- Git 状态。
- 活动时间线。

### 8.3 推荐工作流

项目级工作流建议如下：

```text
需求提出
→ 需求澄清
→ 技术方案
→ 任务拆分
→ 多 worker 并行执行
→ 代码合并 / 冲突处理
→ 测试验证
→ 验收总结
→ 文档归档
```

### 8.4 需求管理

需求不应只存在于聊天消息中，应作为项目内一等对象管理。

功能需求：

- 支持创建需求。
- 支持从对话生成需求。
- 支持编辑需求标题、背景、目标和范围。
- 支持维护验收标准。
- 支持关联会话、方案、任务、文件变更和验收记录。
- 支持需求状态流转。

推荐需求状态：

- 草稿。
- 待确认。
- 已确认。
- 设计中。
- 开发中。
- 待验收。
- 已完成。
- 已废弃。

### 8.5 方案管理

方案用于承接需求到执行之间的设计过程。

功能需求：

- 支持为需求创建一个或多个方案。
- 支持从对话总结生成方案。
- 支持描述影响范围、关键文件、数据结构、接口变化和风险。
- 支持维护测试计划。
- 支持用户批准方案后进入执行。
- 支持方案被驳回后重新调整。

### 8.6 执行任务

任务用于承接具体可执行工作。

功能需求：

- 支持把方案拆分为多个任务。
- 支持任务分配给不同 worker。
- 支持查看任务状态、执行日志、文件变更和测试结果。
- 支持暂停、取消、重试任务。
- 支持任务完成后进入验收。

推荐任务状态：

- 待执行。
- 排队中。
- 执行中。
- 等待用户输入。
- 待验收。
- 已完成。
- 失败。
- 已取消。

### 8.7 验收管理

验收用于判断需求是否真正完成。

功能需求：

- 支持每个需求维护验收标准。
- 支持根据执行结果生成验收报告。
- 支持记录测试命令、测试结果和人工检查结论。
- 支持验收通过。
- 支持验收退回修改。
- 支持验收暂缓。

### 8.8 文档归档

项目应自动沉淀关键过程，不让上下文只散落在聊天里。

功能需求：

- 支持将需求、方案、执行结果和验收报告归档为项目文档。
- 支持从对话中一键归档重要结论。
- 支持任务完成后生成实现摘要。
- 支持项目级决策记录。
- 支持按需求查看相关文档。

推荐文档类型：

- 需求文档。
- 技术方案。
- 决策记录。
- 实现记录。
- 测试报告。
- 验收报告。
- 发布说明。

## 9. 多 Worker 并行与 Git 管理

### 9.1 背景

多 worker 并行可以提升执行效率，但如果多个 worker 直接在同一个工作区修改代码，会造成文件覆盖、状态混乱和 Git 冲突不可控。

因此，多 worker 必须与 Git 工作区隔离能力一起设计。

### 9.2 推荐方案：Git Worktree

每个 worker 使用独立 `git worktree` 和独立任务分支执行。

```text
main workspace
worker-1 worktree -> task/android-host-management
worker-2 worktree -> task/chat-status-ux
worker-3 worktree -> task/project-workflow
```

功能需求：

- 创建 worker 时自动创建独立 worktree。
- 每个 worker 对应独立任务分支。
- 支持展示每个 worker 的当前分支、状态、diff 和测试结果。
- 支持从 worker worktree 合并改动回主工作区。
- 支持检测合并冲突。
- 支持放弃 worker 改动并清理 worktree。
- 支持 worker 分支 rebase 到主分支最新状态。
- 支持限制 worker 可修改范围，降低任务之间互相影响。

### 9.3 合并策略

推荐提供以下合并方式：

- 直接合并：适合无冲突且任务边界清晰的改动。
- 选择性应用：适合只接受部分文件或部分 diff。
- 生成 patch：适合需要人工审查后再应用的改动。
- 放弃改动：适合任务失败或方向错误的 worker。

### 9.4 风险控制

- 合并前展示文件变更摘要。
- 合并前提示冲突风险。
- 合并前可运行测试或构建命令。
- 合并失败时保留 worker worktree，便于用户排查。
- 禁止 worker 自动覆盖主工作区未提交改动。

## 10. 信息架构建议

项目页推荐演进为以下结构：

```text
Project
├─ Overview
├─ Conversations
├─ Requirements
├─ Plans
├─ Tasks
├─ Workers
├─ Git
├─ Docs
└─ Activity
```

### 10.1 Overview

- 展示项目目标、当前进度、活跃任务、待验收项和风险。

### 10.2 Conversations

- 保留现有多会话能力。
- 支持会话关联需求、方案和任务。

### 10.3 Requirements

- 管理项目需求池。
- 展示需求状态、关联任务和验收结果。

### 10.4 Plans

- 管理技术方案。
- 展示方案审批状态、影响范围和任务拆分。

### 10.5 Tasks

- 管理执行任务。
- 展示任务状态、负责人、worker、执行结果。

### 10.6 Workers

- 管理并行 worker。
- 展示 worktree、分支、diff、运行状态和合并动作。

### 10.7 Git

- 展示主工作区状态。
- 展示 worker 分支和合并状态。
- 提供冲突处理入口。

### 10.8 Docs

- 管理项目归档文档。
- 支持按需求、方案、任务进行过滤。

### 10.9 Activity

- 展示项目时间线。
- 记录需求变更、方案审批、任务执行、验收和归档事件。

## 11. 分期计划

### 11.1 P0：恢复与补齐

- 恢复 Android 多主机扫描能力。
- 恢复 Android 主机添加、切换、编辑、删除能力。
- Android 对话列表显示运行中、已完成、失败状态。
- Android 当前对话页显示执行、完成、失败状态。
- 优化 Android 对话切换卡顿。
- Desktop 增加执行器连接信息和移动端连接引导。

### 11.2 P1：统一状态与基础项目对象

- 统一多端主机字段、连接状态和错误码。
- 统一会话任务状态模型。
- 项目层增加需求对象。
- 项目层增加方案对象。
- 项目层增加任务对象。
- 支持会话关联需求、方案和任务。

### 11.3 P2：Worker 与 Git 隔离

- 支持创建 worker。
- 支持 worker 使用独立 Git worktree。
- 支持 worker 分支、diff 和测试结果展示。

- 支持多 worker 并行执行互不污染主工作区。

### 11.4 P3：验收与归档

- 支持需求验收标准。
- 支持生成验收报告。
- 支持验收通过、退回和暂缓。
- 支持项目文档归档。
- 支持从对话归档重要结论。
- 支持项目活动时间线。

## 12. 验收标准

### 12.1 Android 多主机管理

- 用户可以扫描发现可连接主机。
- 用户可以手动添加主机。
- 用户可以保存多个主机。
- 用户可以切换当前主机。
- 用户可以编辑和删除已保存主机。
- 用户可以看到当前连接主机和基础连接状态。
- 旧版本已有的默认主机、最近使用和去重行为得到恢复。

### 12.2 Android 对话体验

- 切换常规长度对话时无明显卡顿。
- 运行中会话在列表中可识别。
- 已完成会话在列表中可识别。
- 失败会话在列表中可识别。
- 当前对话页可看到任务执行、完成、失败状态。
- 任务完成后有明确反馈。
- 不出现“切换到未完成对话时弹窗提示”。
- 不出现“长时间无输出可能卡住提示”。

### 12.3 Desktop 执行器可发现性

- Desktop App 可以被 Android 端通过局域网扫描发现。
- Desktop App 展示移动端连接所需地址和端口。
- Android 端负责添加、编辑、删除和切换多个 Desktop。
- Android 端可以测试 Desktop 连接。

### 12.4 项目级工作流

- 用户可以创建和管理需求。
- 用户可以为需求创建方案。
- 用户可以把方案拆分为任务。
- 用户可以查看任务执行状态。
- 用户可以进行验收并记录结果。
- 用户可以归档需求、方案、实现和验收文档。

### 12.5 多 Worker 与 Git

- 每个 worker 拥有独立 worktree。
- 每个 worker 使用独立任务分支。
- 多 worker 并行执行时不直接污染主工作区。
- 用户可以查看 worker diff。
- 用户可以合并、选择性应用或放弃 worker 改动。
- 冲突可以被检测并提示用户处理。

## 13. 关键原则

- 先恢复旧能力，再考虑新增能力。
- Android 多主机管理不是复杂 runtime 系统。
- 状态展示应清晰但不打扰用户。
- 项目层必须围绕真实交付工作流设计。
- 多 worker 并行必须以 Git 隔离为前提。
- 对话可以是入口，但项目对象和文档才是长期沉淀。

## 14. Workbench 新页面需求增补

本节根据 2026-08-24 Workbench UI 设计稿补充页面级需求。详细规格见 `docs/superpowers/specs/2026-08-24-planrla-workbench-pages-requirements.md`。

### 14.1 全局布局约束

- 所有桌面端子页面必须保留统一左侧图标导航区域。
- 子页面只能切换左侧图标区域右侧的内容区，不得为单个页面重建独立 rail。
- 当前页面通过导航项高亮表达，不通过改变 rail 结构表达。
- 页面弹窗、详情面板、创建面板不得遮挡或重排左侧图标区域。

### 14.2 新增页面

- 项目总览 / Project Overview：展示项目目标、进度、风险、待处理事项、AI 运行状态和五阶段研发流程。
- 消息盒子 / Message Inbox：统一接收外部渠道、团队协作者、AI agent 和系统任务消息。
- 消息线程详情 / Thread Detail：展示线程上下文、附件、AI 协作请求、人工审批、绑定信息和回复入口。
- 研发流程 / Delivery Workflow：以 `需求设计 -> 技术方案 -> 开工 -> 测试验证 -> 交付` 五阶段看板推进项目。
- 日历与定时任务 / Calendar & Schedule：管理会议、提醒、定时任务、一次性任务和 AI 自动推进计划。

### 14.3 消息来源范围

消息盒子需要支持以下来源模型：

- 外部 IM：微信、企业微信、飞书、钉钉、Slack。
- 客服渠道：闲鱼客服、小红书客服、TikTok 客服、抖音客服。
- 团队协作：项目成员、组内协作者、负责人、审查者。
- AI 协作：AI 请求人工确认、补充资料、授权、验收或阶段审批。
- 系统消息：日历提醒、定时任务提醒、一次性任务提醒和交付节点变化。

### 14.4 阶段验收要求

- 用户进入项目后可以从项目总览判断项目是否正常推进。
- 用户可以从消息盒子进入线程详情，并完成回复、审批、转交或关闭。
- 用户可以在研发流程页看到每个阶段的任务数量、负责人、优先级、状态和进度。
- 用户可以在日历页创建每日重复类定时任务和指定时间的一次性任务。
- 消息、任务、日历事件必须支持绑定到项目上下文，后续再逐步绑定到需求、方案、任务和验收对象。
