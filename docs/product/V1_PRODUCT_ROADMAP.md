# Planrla v1 产品迭代路线图

## 背景

当前项目已经完成 MVP 阶段的核心目标：桌面端、Web UI、后端服务、AI Provider、商业授权和 Electron 分发能力已经基本跑通。下一阶段的目标不再只是“能用”，而是让 Planrla 成为一个清晰、稳定、高性能、可扩展的商业级 AI Agent 工作台。

同时，Android 端不应继续作为割裂项目单独演进。建议将 Android 客户端纳入当前工作区，形成统一产品、统一接口、统一发布节奏的一体化研发模式。

## v1 目标

v1 的目标是建立一个可商业交付的基础版本：

- 用户可以低成本理解产品，并快速完成核心任务。
- 桌面端、Web 端、Android 端共享核心业务协议和产品体验。
- 长会话、大项目、多 Provider、多插件场景下保持流畅。
- Provider、插件、授权、更新、企业能力具备持续扩展基础。
- 产品具备商业分发、诊断、升级和客户支持的基础闭环。

## 迭代原则

### 1. 清晰简洁的交互设计

- 默认流程要短，核心路径不依赖用户阅读说明。
- 主界面只保留高频动作，复杂能力进入二级入口。
- 所有异步任务都必须有明确状态：运行中、等待用户、完成、失败、需关注。
- 空状态、加载态、错误态、权限态统一设计，不让用户猜发生了什么。
- 高级能力通过 Command Palette、设置页、高级面板承载，而不是堆满主界面。

### 2. 优异的性能

- 用户输入、会话切换、消息渲染、文件浏览必须保持即时响应。
- 大会话、大文件树、大量项目、大量插件场景必须有增量加载和虚拟化策略。
- WebSocket 高频消息要做合并、节流和事件归类，避免前端无意义重渲染。
- 后端文件扫描、会话同步、Provider 检测、插件更新应后台化、可取消、可观测。
- 性能优化要形成指标，不只依赖主观感受。

### 3. 扩展性强的架构

- Provider、插件、License、更新、移动端能力都要模块化。
- 前端尽量基于能力声明渲染 UI，而不是写大量 provider-specific 分支。
- 后端模块边界要继续从 `server/index.js` 拆出，避免入口文件持续膨胀。
- Android、Desktop、Web 共享协议、类型、错误码、状态机和业务文档。
- 商业能力必须可配置、可灰度、可诊断。

## 工作区一体化策略

### 为什么要纳入 Android

如果 Android 端继续独立开发，会带来几个问题：

- 移动端无法及时复用后端协议和会话状态设计。
- 同一个功能需要在多个仓库重复定义接口、状态、错误码。
- 桌面端和移动端体验不一致，后期修复成本高。
- 商业授权、账号、通知、更新、诊断等能力很难一体化。
- 多端联调依赖人工同步，影响迭代速度。

### 推荐目录结构

建议当前仓库逐步演进为产品级工作区：

```text
apps/
  desktop/            # Electron 桌面壳，可后续从 electron/ 迁移
  web/                # React Web UI，可后续从 src/ 迁移
  android/            # Android 客户端
services/
  api/                # Express 后端，可后续从 server/ 迁移
packages/
  shared/             # 多端共享类型、协议、错误码、状态机
  ui-contracts/       # UI 能力声明、Provider 能力描述
docs/
  product/            # 产品规划、交互规范、路线图
  architecture/       # 架构设计、协议文档、模块边界
  commercial/         # 授权、发布、合规、商业化文档
```

短期不建议马上大规模搬目录。可以先把 Android 作为 `apps/android` 引入，并建立共享协议文档；等边界稳定后再迁移 Web、Electron、Server。

### Android 接入阶段

#### Phase A：代码进入工作区

- 将 Android 客户端放入 `apps/android`。
- 保留 Android 原有构建方式，先不强行改 Gradle 结构。
- 新增根目录说明，标记桌面/Web/后端/Android 的启动方式。
- 确定 Android 与后端通信方式：局域网服务、云服务、还是桌面桥接。

#### Phase B：协议对齐

- 梳理 Android 当前依赖的接口列表。
- 将 REST API、WebSocket 消息、错误码、任务状态整理为共享协议。
- 建立版本化 API contract，避免移动端被后端改动打断。
- 对齐登录、License、Provider、项目、会话、通知能力。

#### Phase C：体验一致

- 对齐项目列表、会话列表、任务状态、完成提醒、设置项。
- 统一命名、图标、状态文案、错误提示。
- 移动端保留轻量交互，不照搬桌面复杂面板。
- 明确移动端核心定位：查看、接管、提醒、轻量操作，而不是完整 IDE。

#### Phase D：联合发布

- 建立桌面端、Web 端、Android 端共同的版本规划。
- 引入 release checklist，覆盖签名、更新、授权、隐私、日志、崩溃。
- 对商业客户支持私有化配置和禁用能力。

## v1 Milestones

## Milestone 1：核心体验打磨

目标：让用户打开产品后，能清楚知道在哪里、能做什么、任务进行到哪一步。

### 需求

- 重构主界面信息架构：项目、会话、对话、文件、Git、终端关系更清晰。
- 完善会话列表倒序和新完成标记，用户点击后取消提醒。
- 增加统一任务状态：运行中、等待权限、完成、失败、需关注。
- 增加任务完成通知，包括桌面通知、声音开关、移动端通知预留。
- 统一空状态、加载态、错误态、权限态。
- 优化设置页分组：常用设置前置，高级设置折叠。
- 增强 Command Palette，作为高级用户的快速入口。

### 验收标准

- 新用户 5 分钟内可以完成一次项目选择、发起任务、查看结果。
- 任意运行中任务都能在 UI 中看到状态。
- 完成任务有明确提醒，不依赖用户停留在当前对话。
- 设置页主要配置项不需要用户反复查找。

## Milestone 2：性能专项

目标：让大项目、长会话、多任务情况下依然保持顺滑。

### 需求

- 聊天消息列表虚拟化，支持长会话不卡顿。
- 文件树增量加载，避免一次性扫描和渲染大目录。
- 项目列表、会话列表缓存和分页加载。
- WebSocket 消息节流、合并和事件分类。
- 后端文件扫描、会话同步、Provider 检测后台任务化。
- 增加前端性能观测点：首次加载、会话切换、首条消息渲染、长会话滚动。
- 增加后端性能日志：接口耗时、扫描耗时、Provider 启动耗时。

### 验收标准

- 1000 条消息会话仍可流畅滚动。
- 大项目文件树首次打开不阻塞主界面。
- 高频流式输出不导致明显输入卡顿。
- 会话切换有可感知的即时反馈。

## Milestone 3：Provider 架构标准化

目标：把多 Provider 从“能接入”升级为“可持续扩展”。

### 需求

- 定义统一 Provider Contract。
- 每个 Provider 声明能力：认证、模型、会话、消息、权限、工具、MCP、技能。
- 前端基于能力声明渲染 UI，减少 provider-specific 分支。
- 后端 Provider 适配层标准化：auth、models、sessions、run、permissions、skills。
- 统一 Provider 错误码和恢复建议。
- 增加 Provider 健康检查和诊断面板。

### 验收标准

- 新增一个 Provider 不需要改动核心聊天 UI。
- Provider 异常可以展示清晰原因和下一步动作。
- 不同 Provider 的模型、会话、权限体验保持一致。

## Milestone 4：Android 一体化

目标：Android 成为 Planrla 产品的一等客户端，而不是附属项目。

### 需求

- 将 Android 客户端纳入 `apps/android`。
- 建立 Android 与当前后端的接口清单。
- 对齐登录、项目、会话、任务状态、完成提醒。
- 移动端支持查看任务、接收提醒、继续对话、轻量审批。
- 建立 Android 调试文档和联调流程。
- 抽取共享协议到 `packages/shared` 或文档化 contract。

### 验收标准

- Android 可以连接同一后端查看项目和会话。
- 桌面端发起的任务完成后，Android 有可接收的状态或通知通道。
- Android 与 Web/Desktop 对同一任务状态展示一致。

## Milestone 5：插件系统产品化

目标：插件从技术能力变成稳定可控的产品能力。

### 需求

- 插件安装、启用、禁用、卸载、更新流程标准化。
- 插件权限声明：文件系统、网络、命令执行、MCP、UI 扩展。
- 插件运行状态和日志可查看。
- 插件错误不影响主应用稳定。
- 预留插件市场和企业私有插件源。

### 验收标准

- 用户能清楚知道插件申请了什么权限。
- 插件失败不会拖垮主进程或核心服务。
- 插件更新和回滚路径明确。

## Milestone 6：商业交付基础

目标：让产品可以面向真实客户部署、授权、更新和支持。

### 需求

- License 支持试用期、离线授权、设备绑定、席位预留。
- 自动更新支持 stable、beta、internal 渠道。
- 增加日志导出、诊断报告、环境检查。
- 增加崩溃和错误反馈入口。
- 增加代理配置、私有更新源、禁用外部网络能力。
- 整理第三方依赖风险处理计划。

### 验收标准

- 客户环境出问题时可以一键导出诊断信息。
- 商业授权状态清晰可见，可离线激活。
- 桌面端更新链路可控，可灰度。

## 风险与约束

- 过早大规模 monorepo 重构会拖慢业务迭代，建议先引入 Android，再逐步抽共享包。
- Provider 差异很大，Contract 需要允许能力缺失，而不是强行统一所有行为。
- 性能问题不能只靠前端优化，后端扫描、同步、CLI spawn 都需要纳入指标。
- Android 端不应复制桌面端复杂功能，移动端定位应更偏通知、查看、接管和轻量操作。
- 商业授权不能阻碍本地开发体验，需要保留明确的开发 bypass。
